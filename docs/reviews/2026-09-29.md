# Выборочное ревью Core и UI — 29 сентября 2026

Проверены фильтры, редактор записей, HTTP-прокси, обновление сессий,
часть кода коллекций, разрешений и истории. Это выборочное ревью,
а не полный аудит безопасности. В Git пока нет истории коммитов,
поэтому авторство отдельных участков не устанавливалось.

## Исправлено

### 1. Потеря несохранённых изменений при переключении разделов записи

`ItemRecordDialog` размонтировал `ItemForm` при переходе в историю или связи.
Локальное состояние формы уничтожалось. Теперь форма остаётся смонтированной
и скрывается на время просмотра соседнего раздела. При закрытии редактора
черновик по-прежнему сбрасывается.

Файл: `apps/ui/src/components/items/item-record-dialog.tsx`.

### 2. Истечение access-токена в открытой админке

API-прокси возвращал 401 даже при наличии действующего refresh-токена.
Теперь он обновляет сессию при отсутствии access-cookie или после ответа 401
от Core и передаёт новые HttpOnly cookies клиенту.

- Повтор запроса выполняется только после отказа аутентификации.
- Ошибки сети, 403 и 5xx не запускают повторную запись данных.
- Новые cookies возвращаются и при сбое запроса, следующего после refresh.
- Недоступность Core при обновлении страницы больше не удаляет cookies.
- Параллельные запросы в одном процессе используют общий refresh.
- Результат refresh используется повторно в течение пяти секунд
  **после завершения** запроса. Раньше таймер начинался
  до ответа и мог допустить вторую ротацию ещё выполняющегося запроса.

Файлы: `apps/ui/src/lib/core-proxy.ts`, `core-session-request.ts`,
`renew-session.ts`, `session-cookies.ts`; маршруты login и auth/renew.

### 3. Фильтры по фрагментам email

`contact содержит @example` возвращал 400: операнд фильтра проходил проверку
полного email. Для текстовых операторов разрешены фрагменты; ограничения
длины и пустых значений сохранены. Создание и изменение email по-прежнему
требуют корректного адреса.

Файл: `apps/core/src/items/filter-input.ts`.

### 4. Краевые случаи нового выбора связанных записей

Кеш подписей переведён на `Map`: ручные строковые ключи вроде `constructor`
или `toString` больше не конфликтуют с унаследованными свойствами объекта.
Длина строки поиска ограничена 100 символами, согласно контракту Core.

Файлы: `apps/ui/src/components/items/use-filter-relation-items.ts`,
`item-filter-relation-value.tsx`, `item-filter-menu.tsx`.

## Следующие задачи

1. **Полнота истории при каскадах — высокий приоритет.** `deleteItem` пишет
   событие только для непосредственно удаляемой записи. Настройки связей
   допускают CASCADE, SET NULL и SET DEFAULT, но изменения зависимых записей
   не проходят через `recordItemEvent`. Нужен отдельный выбор механизма учёта
   и передачи actor/requestId; текущее обещание «любые изменения через API»
   такими каскадами не покрывается.
2. **Защита входа и обслуживание токенов — до публичного запуска.** В Core
   нет ограничения частоты попыток входа/обновления токенов. Это требование
   уже записано в `docs/design/authentication.md`. Также не найден механизм
   удаления истёкших сессий и старых токенов. Общий refresh-кеш UI действует
   только внутри одного процесса: несколько реплик требуют координации
   ротации, иначе повтор refresh может отозвать сессию. Сценарий нескольких
   реплик этим ревью не проверялся.
3. **Рост истории и персональные настройки — следующий этап.** Для событий
   не найдено реализованного срока хранения/архивации. Его нужно задавать
   явно, сохраняя возможность длительного аудита. Настройки колонок сейчас
   лежат в localStorage под ключом коллекции без userId, поэтому разные
   пользователи одного браузера делят оформление. Идея персональных
   настроек уже описана в `docs/ideas/user-ui-preferences.md`.
