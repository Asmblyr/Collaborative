# Ревью качества кода Asmblyr Collaborative

Дата: 2026-10-01. Предмет: Core, UI, контракты между ними, миграции и организация проверок.

Последующий этап: [реализованные исправления R1–R9 и проверки](2026-10-01-quality-fixes.md).
Ниже сохранены исходные наблюдения до исправлений.

## Вывод

Проект уже имеет рабочее разделение по предметным областям, общие компоненты интерфейса и содержательные интеграционные тесты. Основной долг сейчас — согласованность операций между модулями: полное сохранение настройки поля, единое понимание типов связей, подключение жизненного цикла форм и обработка ошибок.

Ниже — **9 замечаний**, из них одно P1 и восемь P2, затем отдельно известное ограничение истории и рекомендации по переиспользованию. P1 стоит закрыть до открытия сервиса внешним пользователям; P2 — в ближайшем этапе стабилизации. Приоритет здесь означает порядок исправления, а не оценку объёма работы.

Продуктовый код в рамках ревью не менялся. Добавлены этот отчёт и локальные диагностические скрипты в игнорируемой `.local-data/`.

## Замечания

### R1 · P1 · Парольный вход не ограничивает частоту попыток

**Где:** [auth/routes.ts](../../apps/core/src/auth/routes.ts), строка 37; [auth/rate-limit.ts](../../apps/core/src/auth/rate-limit.ts), строка 4.

`/auth/login` зарегистрирован без ограничителя. Для `/auth/refresh`, setup и принятия приглашения он также не подключён. Общего ограничения в `createApp` нет. Уже существующий `credentialRateLimit` используется для сервисных токенов, федераций, смены пароля и загрузки файлов.

**Проверка:** 80 последовательных неудачных попыток входа с одного адреса вернули 401; ни одного 429. Код подтверждает, что ограничителя нет и для попыток с существующим email, где дополнительно выполняется Argon2.

**Последствие:** публичный парольный вход допускает неограниченный перебор и нагрузку на проверку паролей.

**Исправление:** согласованно ограничить публичные credential endpoints. Для логина учитывать источник запросов и нормализованный аккаунт. При работе через Next BFF Core видит адрес BFF: нужно определить доверенную передачу адреса клиента или ограничивать на входе BFF. Простое добавление лимита по `request.ip` создаст общий лимит для пользователей админки.

### R2 · P2 · «Сохранить поле» выполняет несколько независимых изменений

**Где:** [field-editor-form.tsx](../../apps/ui/src/components/collections/field-editor-form.tsx), строки 86–140; [collections/service.ts](../../apps/core/src/collections/service.ts), строки 176–193; [field-presentation.ts](../../apps/core/src/collections/field-presentation.ts), строки 41–44.

Форма последовательно сохраняет структуру/default, поиск, поиск по связи и отображение. Каждый HTTP-запрос фиксируется отдельно. При отказе последующего запроса предыдущие изменения остаются в БД.

Есть и ошибка порядка валидации: новый default проверяется по старому набору вариантов select, а новый набор вариантов — по старому default.

**Воспроизведено:**

1. У поля select единственный вариант `a`, default — `a`.
2. Пользователь заменяет вариант на `b` и выбирает default `b`.
3. Сохранение default первым получает 400: `Value is not one of the configured choices`.
4. Обратный порядок также получает 400: `Current default does not match the new settings; change it first`.
5. Отдельно проверено: успешное изменение `required`, затем ошибочное отображение — `required` уже сохранён, несмотря на ошибку общего действия.

**Исправление:** команда сохранения полного предполагаемого состояния поля; проверять согласованность итоговых настроек и атомарно сохранять структуру/default/presentation/метаданные. Уже существующие сервисы можно вызвать из одного прикладного сценария. `CREATE INDEX CONCURRENTLY` требует отдельного жизненного цикла вне транзакции: явно возвращать его состояние и возможность повторить операцию.

### R3 · P2 · Защита несохранённых изменений подключена только к части редакторов

**Где:** [collections-workspace.tsx](../../apps/ui/src/components/collections/collections-workspace.tsx), строки 117–165; [editor-dialog.tsx](../../apps/ui/src/components/collections/editor-dialog.tsx), строки 22–23 и 81–85.

Общий `EditorDialog` получает `settingsState.dirty/busy`, но обновляет их только `CollectionSettingsForm`. Редакторы поля, создания связи, создания коллекции и организации формы этого контракта не имеют. Их собственный `pending` недоступен оболочке.

**Следствие из кода:** изменение настроек поля или раскладки формы → Escape/«Закрыть» закрывает редактор без подтверждения. Во время сохранения оболочка тоже допускает закрытие. Запрос может закончиться после закрытия окна, когда пользователь уже потерял контекст результата.

**Исправление:** единый небольшой контракт состояния редактора `{ dirty, busy }` для всех форм, использующих эту оболочку; отдельно обрабатывать запрос на отмену и завершение успешного сохранения. Проверить Escape, верхнюю кнопку закрытия, переход назад и закрытие во время запроса. В этом ревью замечание установлено чтением кода; новый браузерный прогон этих действий не выполнялся.

### R4 · P2 · Редактирование связи повторно определяет её тип как обычный столбец

**Где:** [collections/service.ts](../../apps/core/src/collections/service.ts), строки 166–185; [field-types.ts](../../apps/core/src/collections/field-types.ts), строка 6. Для сравнения: [schema-repository.ts](../../apps/core/src/items/schema-repository.ts) учитывает `asmblyr_relations`.

`updateCollectionField` читает тип PostgreSQL и semantic type, но не метаданные связи и тип её целевого ключа. Для FK на `bigserial` физический тип — `bigint`; `fieldTypeFromDatabase` возвращает `null`. Существующий default при любом изменении поля заново валидируется через этот неверный тип.

**Проверка:** создать M2O на коллекцию с `bigserial`, `onDelete: setDefault`, существующим ID по умолчанию. Изменить только `required: true` → 400 `Invalid default value for field: big`.

Для строкового ключа физический `character varying` также отсутствует в этом маппере; этот вариант установлен по коду, отдельно не воспроизводился.

**Исправление:** использовать общее описание поля с вариантом `relation` и типом целевого ключа; валидировать default связи через тот же контракт ID, который используется при её создании и записи items. Это конкретный случай, где переиспользование устраняет уже существующий дефект.

### R5 · P2 · SQL-алиасы фильтров конфликтуют с допустимыми именами коллекций

**Где:** [filter-query.ts](../../apps/core/src/items/filter-query.ts), строки 49–59.

В коррелированном подзапросе жёстко заданы алиасы `related` и `bridge`, а внешняя таблица адресуется по `sourceName`. Коллекции с такими именами разрешены. Внутренний алиас перекрывает внешнее имя.

**Проверка:** коллекция `related`, связь `owner` на другую коллекцию, фильтр `owner.name = Ada` → 500 с `column related.owner does not exist`. Такой же набор данных в коллекции `review_plain` → 200. Если совпадающее имя столбца есть и во внутренней таблице, возникает риск неверной корреляции вместо явной ошибки.

**Исправление:** назначать внешнему источнику собственный SQL-алиас и передавать его в построитель условий; алиасы вложенных источников генерировать независимо. Покрыть `related`, `bridge` и связь коллекции на себя. Ограничивать продуктовые имена ради внутренних алиасов не требуется.

### R6 · P2 · Readiness сообщает готовность при несовместимой структуре БД

**Где:** [app.ts](../../apps/core/src/app.ts), строки 57–173; [catalog-repository.ts](../../apps/core/src/collections/catalog-repository.ts), строка 56.

Readiness содержит вручную поддерживаемый перечень таблиц, столбцов и CHECK. Последние `display_name`, `mcp_enabled`, `mcp_description`, `hidden`, `parent_collection` в нём отсутствуют, хотя текущие запросы их требуют.

**Проверка:** во временной БД переименован только `mcp_description`, чтобы имитировать отсутствие ожидаемого столбца. `/ready` → 200, `/collections` → 500. Столбец возвращён, временная БД удалена.

**Исправление:** отдельный модуль readiness с проверкой обязательных миграций; при необходимости поддержки ручных изменений БД — дополнительно небольшие проверки критических инвариантов. Компонент сборки приложения должен регистрировать эту проверку, а не содержать большой вручную синхронизируемый SQL-список.

### R7 · P2 · Интеграционные тесты по умолчанию работают с БД приложения

**Где:** [assistant-settings.integration.test.ts](../../apps/core/test/assistant-settings.integration.test.ts), строки 15–26, 60 и 104; [item-events.integration.test.ts](../../apps/core/test/item-events.integration.test.ts), строка 105; [core/package.json](../../apps/core/package.json), строки 13–15.

Тесты загружают `.env` и используют `DATABASE_URL`. Выделение тестовой базы или проверка безопасного назначения подключения отсутствуют. Многие тесты аккуратно создают собственные fixtures, но некоторые изменяют общие объекты: настройки ассистента и структуру таблицы истории.

**Последствие:** обычный запуск тестов может временно менять настройки работающей админки и блокировать её запросы. Восстановление старого значения в `finally` также может затереть параллельно сохранённую настройку пользователя. При аварийном завершении процесса `finally` не гарантирует очистку.

**Исправление:** штатный runner создаёт отдельную временную БД, применяет миграции и удаляет её после тестов; тесты отказываются работать с обычным `DATABASE_URL` без явно определённого тестового контекста. В этом ревью все DB-тесты выполнены именно в изолированных базах.

### R8 · P2 · Нет единого запуска всех автоматических проверок

**Где:** [package.json](../../package.json), строка 16; [core/package.json](../../apps/core/package.json), строки 13 и 15; [ui/package.json](../../apps/ui/package.json), строки 5–10.

Корневой `test:integration` запускает только перечисленный вручную набор Core. Assistant имеет отдельную команду внутри пакета. У UI есть 12 файлов с 42 unit-проверками, но нет `test` script. Typecheck и lint эти тесты не исполняют.

**Последствие:** стандартный зелёный прогон не покрывает модель фильтров, черновики, дерево коллекций, обновление сессии и остальные UI-модели. Добавление нового Core test-файла также требует вручную изменить длинную строку запуска.

**Исправление:** явные команды `test:unit`, `test:integration`, `test:all`; обнаружение файлов внутри определённых тестовых наборов. BFF/browser/cloud smoke должны иметь отдельный запуск и явное окружение: например, `files-ui.integration.test.ts` сейчас обращается к работающему `127.0.0.1:3000`, и включать его в общий glob без изоляции нельзя.

### R9 · P2 · Неожиданные ошибки БД уходят в API вместе с SQL

**Где:** [app.ts](../../apps/core/src/app.ts), строка 32 и регистрация маршрутов; [items/routes.ts](../../apps/core/src/items/routes.ts), строки 22–29.

Единого `setErrorHandler` нет. Известные ошибки в отдельных сервисах преобразуются в доменные, но неизвестные Knex/PostgreSQL ошибки проходят к стандартному ответу Fastify.

**Проверка:** ответ на R5 содержит полный текст `select * from ...`, имена таблиц/алиасов и сообщение PostgreSQL. Это одновременно раскрытие внутренних деталей и непригодное для интерфейса сообщение.

**Исправление:** общий формат ошибки `{ code, message, requestId }`; для непредвиденного 500 — безопасное сообщение, детали в серверном журнале. Существующие понятные доменные 4xx сохранять. В UI использовать код ошибки вместо разбора текста. Общий обработчик должен сопровождать исправление причины R5.

## Известное функциональное ограничение: история каскадных изменений

**Где:** [items/service.ts](../../apps/core/src/items/service.ts), строки 94–107; [relations.ts](../../apps/core/src/collections/relations.ts), создание FK; [README.md](../../README.md), строки 300–301.

Это уже явно документированное ограничение, а не новая регрессия. Удаление через API пишет событие только для запрошенной записи. Действия PostgreSQL `SET NULL`, `SET DEFAULT`, `CASCADE` над связанными строками не проходят через `updateItemRow`/`recordItemEvent`.

**Воспроизведено:** удалить родителя с `SET NULL` → внешний ключ ребёнка изменился с `1` на `null`, история ребёнка содержит только `create`, его `updated_at` не изменился.

С учётом договорённости «записывать любые изменения через API» это существенный долг. Требуется единая стратегия учёта побочных изменений: прикладное выполнение с аудитом или транзакционные триггеры с явно переданным контекстом актора/запроса. Выбор влияет на поведение прямых SQL-записей, порядок блокировок и объём истории; его стоит зафиксировать отдельно. Проверка реальных ссылок перед удалением файла уже компенсирует устаревание индекса файлов, поэтому из этого наблюдения не следует утечка доступа к файлам.

## Качество, чистота и переиспользование

### Что уже работает хорошо

- Core владеет БД; UI обращается через серверный BFF. Маршруты преимущественно делегируют предметным сервисам.
- Политики и разрешения разделены, связи многие-ко-многим сохранены. Итоговые права вычисляются централизованно.
- `itemReadQuery` переиспользуется обычным API и чтением ассистента. Ассистент повторно проверяет доступ; DB-чтения ограничены временем и выполняются в read-only транзакции.
- Запись items, непосредственная история и ссылки файлов сохраняются транзакционно. Для вложенных черновиков уже есть единая команда commit — полезный образец для R2.
- Есть общий `EditorDialog`, единая форма items, shadcn-компоненты и отдельные модели фильтров/черновиков/дерева.
- Пароли хешируются Argon2id, непрозрачные токены хранятся хешами, refresh вращается с выявлением повторного использования. У GitLab assertions проверяются подпись, issuer/audience, оба project ID, ветка и повторное использование.
- Прогон миграций с нуля прошёл. В просмотренных down-миграциях есть проверки отказа от удаления настроенных данных.
- Граф статических импортов не обнаружил недостижимых исходных файлов: 141 в Core, 299 в UI. Это не доказательство отсутствия отдельных неиспользуемых экспортов.
- Самые большие рукописные UI-модули — редактор поля (328 строк) и создание связи (322). `ui/sidebar.tsx` — 702 строки компонента shadcn; размер этого файла сам по себе не требует переделки.

Повторная загрузка каталога установлена по цепочке вызовов. Время ответа на сотнях коллекций или сотнях тысяч строк в этом ревью не измерялось. Начальный шаг оптимизации — один согласованный снимок метаданных на запрос; общий процессный кэш потребует отдельной политики инвалидации после DDL.

### Читаемость

Есть короткие по числу строк, но плотные модули: несколько изменений состояния, условий и JSX-блоков на одной строке. Это заметно в настройках связей, формах и некоторых сервисах. Полезно развернуть обработчики в обычные блоки и выделить повторяемые секции формы. Критерий разделения — самостоятельный сценарий или ответственность; число строк использовать как сигнал к просмотру.

Смешивание формата ответа HTTP и DTO в `components/access/types.ts`, а также универсальных валидаторов в сервисных аккаунтах мешает ориентироваться в зависимостях. Начать стоит с этих уже общих функций, затем с контрактов полей и формы.

### Границы проверки

Это обзор архитектуры всего репозитория, импортов, тестовых наборов и ручная проверка ключевых путей каждого подсистемного блока. Построчное чтение всех 31 тыс. строк и всех вариантов взаимодействия в браузере не выполнялось. В фокусе были schema/items/relations, авторизация и права, файлы и федерации, preferences/workspaces, AI, формы и BFF.

Production build UI, browser/BFF smoke с живыми сервисами, реальный облачный S3/OIDC обмен, платные AI-вызовы, нагрузочный тест и полный перебор конкурентных DDL/CRUD не выполнялись. Для миграций проверено применение на чистую БД; обновление копии рабочей БД со всеми историческими состояниями отдельно не моделировалось. Работающая админка и её БД в ходе проверок не изменялись.
