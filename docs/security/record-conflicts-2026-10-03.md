# Проверка защиты черновика от перезаписи

Дата: 3 октября 2026. Область: атомарный item commit, HTTP SDK, Kit и боковой редактор.

## Реализовано

`expectedValues` проверяет исходное содержимое изменяемых полей под PostgreSQL row lock. Проверка выполняется после write authorization и требует свежей read-проекции этих полей, включая условные grants. Конфликт возвращает общий `409 ITEM_CHANGED` без значений записи. Вложенные записи, FK и атрибуты junction используют ту же проверку и транзакционный rollback. Повторные обращения к одной записи в пределах commit сравниваются с первым заблокированным снимком.

UI сохраняет свой черновик, читает актуальные значения через обычный авторизованный API и показывает компактный выбор. Применение выбора обновляет исходный снимок; запись выполняется только следующим явным сохранением с повторной проверкой. UI-метаданные не отправляются в Core, а исходные значения отправляются только для изменяемых полей.

## Границы

Это проверка содержимого полей, без новой таблицы версий, миграции, WebSocket или Redis. Она не требует timestamps. Несовпадающие правки разных полей не блокируют друг друга. JSON/массив/rich text — одно значение. Список связей изменяется явными операциями attach/detach, без сравнения всего списка. Изменение и возврат поля к исходному значению не считаются конфликтом.

Пропуск expectedValues сохраняет совместимость обычных клиентов. Незащищённый PATCH, массовые изменения и SQL могут заменить данные; следующий защищённый commit обнаружит несовпадение. Черновик находится в памяти открытой панели и не сохраняется после перезагрузки. При удалении записи, отзыве чтения или сетевой ошибке UI сохраняет черновик в открытом окне, но не обходит доступ.

## Источники и проверки

- Core: `src/items/expected-values.ts`, `update-service.ts`, `record-draft.ts`, `relation-links.ts`.
- Контракт: `packages/contracts/src/item-commit.d.ts`; SDK и Kit используют общий writer.
- UI: `draft-conflicts.ts`, `draft-conflict-review.tsx`, `item-editor-dialog.tsx`.
- Автоматические проверки: `apps/core/test/record-conflicts.integration.test.ts`, `apps/ui/test/draft-conflicts.test.ts`.

Подтверждённые результаты:

- Полный `pnpm test:all` до завершающих уточнений: SDK 13, Core 300, UI 86 passed; 1 существующий opt-in тест LavinMQ skipped.
- После уточнений: `node scripts/test.mjs core-sdk` — 109 passed, включая 10 сценариев конфликтов; `pnpm --filter @asmblyr/ui test:unit` — 89 passed.
- `pnpm -r typecheck`, `pnpm lint` и `pnpm build` прошли. Интеграционные тесты работали только на одноразовой БД runner.
- В Chrome проверены два одновременных редактора одной временной записи: конфликт сохраняет черновик, выбор своего значения требует явного повторного сохранения, выбор актуального убирает изменённость формы. Временная запись и её тестовая история удалены, исходная запись не изменена.

Интеграционный файл оставлен единым, хотя превышает 350 строк: сценарии используют один одноразовый HTTP/Kit fixture и последовательно дополняют его grants и связанные схемы. Деление дублировало бы настройку и скрывало бы общий контекст проверки.

Production-развёртывание, WebSocket и совместное редактирование в реальном времени не входят в эту проверку.
