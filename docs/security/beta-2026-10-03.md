# Первая бета: проверка 03.10.2026

Согласованная граница: отдельная установка на каждую команду. Workspaces не являются tenants. Выпуск проверяется локально в отдельном Docker-окружении; production-хостинг этим результатом не подтверждается.

## Что реализовано

- Одноразовые приглашения по ссылке с прямым входом без SMTP и пароля; настройка первого пароля, passkey и существующий SSO.
- WebAuthn на SimpleWebAuthn 14: подпись, origin/RP ID, UV, одноразовый challenge, счётчик, привязка регистрации к сессии, свежий вход для изменений.
- Superuser-восстановление обычного пользователя; операторское восстановление администратора. При claim/reset отзываются прежние сессии/credentials/OAuth-согласия.
- Файловые grants files/read и files/update для людей; выбор нового файла требует права библиотеки и записи поля. Сервисный principal не получает библиотеку через human settings grant.
- Общие PostgreSQL credential/AI лимиты, предел шагов/контекста модели, очистка временных данных и опциональная очистка истории, приватные logs и ротация.
- Production Docker build, GitLab verification/manual release job, миграционный шаг и runtime compose. Отдельный локальный S3/PostgreSQL стенд, backup/restore/status и smoke на 50 000 записей.
- Удалены демонстрационные обсуждения/уведомления общего виджета. Комментарии записей плагина сохранены.

## Проверки и пределы доказательств

Автоматические негативные проверки покрывают одноразовый/concurrent claim, повтор WebAuthn, другой origin, отсутствие UV, истёкший/cross-session challenge, устаревший счётчик, отключённого пользователя, удаление последнего способа входа, запрет manager recovery, отзыв сессии, file grants/отзыв/чужое скачивание, общий bucket/lease, retention по умолчанию и очистку по возрасту, маскирование logs и предел обращений к модели.

В Chrome подтверждён вход нового обычного редактора по ссылке без пароля, открытие его безопасности и разрешённой библиотеки. Реальный аппаратный passkey/синхронизация устройств требует проверки на устройстве пользователя: криптографические fixtures проверяют сервер и HTTP/BFF без изменения системного credential store.

Локальный HTTP smoke на 50 000 записей: список p95 22 мс; глубокая страница 14 мс; сортировка текста 19 мс; широкий поиск 33 мс; точечный поиск 36 мс. Это 20 последовательных запросов каждого типа внутри Docker на данной машине, не конкурентный production benchmark.

Полный прогон: SDK 13, Core 313, UI 92 — **418 успешных тестов**, один LavinMQ integration пропущен без настроенного брокера. Финальные typecheck, lint, Docker production build и docs generate/check/build прошли. OpenAPI содержит 162 маршрута. После последних auth-проверок повторный focused `core-beta` завершился 6/6.

HTTP/BFF проверка через собранный UI подтвердила signed WebAuthn registration/login, cookie binding challenge, отсутствие tokens в JSON успешного входа, foreign-origin 403, replay 401, recovery с отзывом прежней сессии и необязательный первый пароль. Пользовательские WebAuthn keys ОС при этом не создавались.

Согласованная PostgreSQL/object-volume копия восстановлена в новый `asmblyr-restore-check`: fingerprints **50 таблиц** совпали, все **50 001 запись** на месте (50 000 seed + одна созданная в Chrome), восстановленный вход работает, SHA-256 скачанного файла совпал. Затем операторская recovery-проверка только на этой копии подтвердила отказ старого пароля/сессии, рабочий новый пароль и запрет перезаписи файла credentials.

Четыре новые additive migrations применены и к локальной dev-БД: passkeys/recovery, files grants, общие limits и retention indexes. Рабочие пароли/ключи dev-пользователей не сбрасывались. Проверка CI/release job в реальном GitLab не запускалась; конфигурация подготовлена и локальные эквивалентные проверки прошли. По решению пользователя публичное размещение не входит в этот этап.

## Перед публичным запуском

На выбранном хостинге должны быть настроены и проверены HTTPS origin/прокси, приватные ACL/IAM, backup PostgreSQL и полного bucket с расписанием, проверка восстановленной копии и канал uptime/backup алертов. SMTP не блокирует бету. Нет отдельного MFA flow, per-object ACL, antivirus, денежных AI budgets или плагинной песочницы. Внешние JWT имеют короткий срок действия и не могут быть удалены из приложения получателя.
