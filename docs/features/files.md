# Файлы и объектное хранилище

Файл — отдельная сущность с метаданными в PostgreSQL и содержимым в настроенном S3/YC backend. Поля коллекций хранят ссылки на файлы; пользовательский доступ к содержимому проверяет Core.

| Операция                               | Текущий допуск                                               |
| -------------------------------------- | ------------------------------------------------------------ |
| Список библиотеки, история файла       | Человек + files/read (либо update); superuser                |
| Загрузка, изменение, удаление          | Человек + files/update; superuser                            |
| Метаданные/скачивание связанного файла | files/read, superuser либо read доступ к полю с этой ссылкой |
| Resolve списка ссылок                  | Только разрешённые для principal ссылки                      |

Скачивание по умолчанию — attachment/octet-stream; preview выставляет ограничительную CSP и nosniff. Ограничение загрузки — 25 MiB; загрузка буферизуется в памяти. Секреты хранилища не передаются клиенту.

Поддерживается Yandex IAM token provider, включая настройку федеративного обмена. Это инфраструктурная конфигурация Core; пользовательская федерация GitLab CI для входа в Asmblyr — другой механизм.

Параметры хранилища задаются в [подключениях админки](./connections.md) либо в окружении Core по `apps/core/.env.example`. Env-конфигурация блокирует редактирование группы в админке. Bucket и IAM создаёт оператор своей установки.

Для выбора новой файловой ссылки в поле нужен files/read и право записи этого поля. Уже сохранённую ссылку можно читать через разрешённую запись без доступа ко всей библиотеке. При отзыве files/read библиотека и выбор новых ссылок закрываются; интерфейс загрузки/редактирования отключён для files/read без update.

Библиотека общая для одной установки команды: files/read открывает все её файлы, а не только собственные загрузки. Отдельных прав на каждый объект пока нет. Workspaces не разделяют файлы на tenants. Локальные инструменты установки сохраняют согласованные PostgreSQL и S3 копии при остановленных авторах; [backup/restore](../development/operations.md) описан отдельно.

## Публичная ссылка на один файл

Новые и существующие файлы имеют `visibility: "private"`. Человек с `files/update`
(либо superuser) может изменить видимость одного готового файла на `public` через
боковой редактор или `PATCH /files/:id`. После сохранения появляется кнопка
копирования ссылки. Неправильное значение видимости отклоняется.

`GET /public/files/:id/content` в Core и `/api/public/files/:id/content` в UI
возвращают байты опубликованного файла без сессии. `?preview=1` разрешает только
уже поддержанные растровые превью. Публичного списка и метаданных нет, приватные
маршруты сохраняют свои проверки доступа. Это явная публикация для любого
обладателя ссылки, а не персональное приглашение. Ссылка не содержит IAM/SDK
токенов, bucket остаётся приватным.

При возврате к `private`, удалении либо состоянии не ready публичный маршрут
отвечает 404 до обращения к хранилищу. Ответы используют `no-store`, CSP и
`nosniff`; загрузка по умолчанию — attachment. Отзыв останавливает будущие
скачивания, но не отзывает уже полученные байты или начатый поток.
Прокси UI передаёт только путь и параметр preview, без cookies/Authorization.

Открыто: квоты общего объёма, проверка вредоносного содержимого, преобразования/превью как сервис и reconciliation оставшихся объектов. PostgreSQL и S3 не образуют одну транзакцию. Приватность и резервирование внешнего bucket проверяет оператор конкретной установки.

Источники: `apps/core/src/files`, `apps/core/src/files/storage`. ACL внешнего bucket проверяет оператор своей установки.
