# Совместное редактирование: Directus и предложение для Asmblyr

Дата: 3 октября 2026. Статус Asmblyr: **предложение**, транспорт, leases и версии записей ещё не реализованы.

## Что есть в Directus

Начиная с 11.15 совместное редактирование встроено в ядро. В редакторе видны участники; активное поле получает владельца и временно недоступно другим. Изменения передаются через WebSocket с проверкой прав. Функция включается в настройках проекта; несколько экземпляров сервера используют Redis для координации.

Источники: [обзор](https://directus.com/docs/guides/content/collaborative-editing), [релиз 11.15 от 12 февраля 2026](https://directus.com/resources/directus-11-15-release), [конфигурация](https://directus.com/docs/guides/content/collaborative-editing/configuration).

Есть ограничения: переводы блокируются целой формой; редактирование связей в drawer блокирует интерфейс связи целиком. Совместные изменения могут не сохраниться, если включают поле, на изменение которого у сохраняющего пользователя нет права. [Использование и ограничения](https://directus.com/docs/guides/content/collaborative-editing/usage).

Встроенные обёртки формы автоматически отслеживают фокус и изменение значения. Кастомный редактор должен соблюдать disabled; для порталов нужен контроль focusout. [Контракт интерфейсов](https://directus.com/docs/guides/content/collaborative-editing/development).

Документация не подтверждает универсальную защиту от устаревшего сохранения через произвольный API-клиент. Блокировки полей нельзя считать доказательством такого контракта.

## Что есть в Asmblyr сейчас

- Запись открывается в общей правой панели. UI хранит черновик до явного сохранения; вложенные изменения сохраняются атомарным commit.
- `updateItemRow` блокирует строку на время транзакции и проверяет права до/после изменения. Версия черновика в запросе не проверяется: поздний запрос может заменить более новое значение того же поля.
- Настройки плагинов уже требуют revision и возвращают конфликт для устаревшего сохранения. Это отдельный ресурс, не готовая защита обычных items.
- В Core нет общего WebSocket-транспорта совместного редактирования. Обсуждения и история не заменяют его.

Источники кода: `apps/core/src/items/update-service.ts`, `apps/core/src/items/record-draft.ts`, `apps/core/src/plugins/settings-repository.ts`, `plugins/comments/ui/hooks/use-comments.ts`, `apps/ui/src/components/items`.

## Предлагаемый UX

Режим включается опционально для коллекции; общий переключатель проекта может задавать значение по умолчанию. Пользователю не нужно выбирать режим при каждом открытии записи.

В заголовке правой панели — компактные аватары участников. У занятого поля — аватар и подпись «Редактирует Анна». Остальная форма доступна согласно личным правам. Одновременно работать с разными полями можно; одно поле получает одного владельца. Первая версия блокирует связи, repeater и rich text как единое поле.

Явное сохранение сохраняется. Чужие несохранённые значения не становятся частью запроса пользователя автоматически. Это предотвращает ситуацию, когда один пользователь сохраняет чужие закрытые поля. Чужой черновик можно показать как временное состояние с владельцем, но он не заменяет локальное значение или сохранённое состояние без явного правила слияния.

После сохранения коллегой обновляются только чистые локальные поля. Изменённое с обеих сторон поле показывает конфликт «Ваше значение / Актуальное значение» с осознанным выбором. Принудительная перезагрузка не уничтожает черновик. Потеря связи показывает статус и отключает приобретение новых блокировок; черновик остаётся на месте.

## Предлагаемый контракт

1. Сначала добавить серверную версию записи и проверку expected revision для UI-сохранения, включая вложенные изменения. Версия не зависит от наличия пользовательского updated_at; конфликты возвращают 409 без частичного commit. Решение о совместимости обычного PATCH/Kit/MCP принимается явно: проверка только в UI не защищает внешние записи.
2. Затем presence и блокировки: Core выдаёт lease на `(collection, item, field)`, продлевает heartbeat, освобождает при уходе/сохранении и по TTL. Новый транспорт аутентифицирует человека и проверяет свежие read/update, поля и row conditions. Запреты и отзыв прав должны закрывать уже открытую подписку.
3. Сохранённые изменения публикуются только после commit. Каждому подписчику проецируются исключительно доступные ему поля. ID закрытой строки, значения, старые данные, drafts, аватары и сведения о присутствии также требуют проверки видимости; presence не должен раскрывать закрытые записи.
4. Несохранённые previews — отдельный канал, ограниченный read и field grants; минимальная версия может вообще передавать только presence и факт занятого поля. Передача rich text через CRDT — отдельный этап, без новой зависимости в первом шаге.
5. Для нескольких Core-серверов нужен общий координатор (например Redis). Однопроцессный реестр не является production-моделью для нескольких реплик. Добавление координатора — отдельное согласование зависимости.
6. События имеют версию, сессию и владельца. Reconnect получает сохранённый снимок и состояние leases; устаревшие события игнорируются, повторные сообщения не применяются дважды.
7. Plugin field interfaces подключаются через host wrapper; они сохраняют readOnly, dirty draft и портал формы. Обычные custom inputs не должны самостоятельно выдавать leases или обходить Core.

## Порядок работы и проверка

Первый этап — защита сохранения без realtime: две открытые формы, пересекающиеся/непересекающиеся изменения, внешняя запись, отсутствие timestamp, atomic rollback вложенного commit. Далее опциональный presence/leases, а затем previews и масштабирование.

Проверить: закрытые поля/строки, разный набор grants участников, отзыв политики без нового токена, отключённый аккаунт, разрыв связи/TTL, два сервера, устаревший клиент, потерянные/повторные события, nested/relation editing и plugin input. Изменение схемы версий и публичного writer-контракта требует отдельного согласования перед реализацией.
