# Эксплуатация и восстановление

Одна команда использует отдельную установку, PostgreSQL и приватный bucket.
SMTP необязателен: администратор может вручную передать приглашение или ссылку
восстановления. Workspaces не разделяют данные компаний.

## Сборка и установка

Dockerfile собирает единый образ Core/UI с закреплённым Node image digest, pnpm
и lockfile; приложения работают от пользователя `node`. UI доступен на порту
`3000`, Core API — на `3001`. PostgreSQL и S3 подключаются отдельно.
GitHub workflow проверяет типы, lint, тесты, документацию, production build и
запуск контейнера с одноразовым PostgreSQL перед публикацией образа в GHCR.

[Шаблоны установки](https://github.com/Asmblyr/Collaborative/blob/main/deploy/README.md)
включают локальную установку с S3 и вариант для внешних PostgreSQL/bucket.
Миграции выполняются перед Core. Для публичной установки нужны HTTPS reverse proxy,
точный внешний `AUTH_UI_URL`, приватные БД и bucket. OAuth signing keys сохраняйте
между выпусками и резервируйте отдельно.

Перед обновлением создайте копию данных и проверьте миграции на восстановленной
установке. Откат образа допустим только с совместимой схемой; разрушительный
rollback миграций не заменяет восстановление.

## Копии локальной Docker-установки

Следующие инструменты обслуживают только `deploy/local/compose.yaml`:

```sh
node scripts/operations/backup.mjs /private/asmblyr.env asmblyr-local /private/backups/new-copy
node scripts/operations/restore.mjs /private/restore.env asmblyr-restore-check /private/backups/new-copy
node scripts/operations/status.mjs /private/restore.env asmblyr-restore-check
```

Backup останавливает UI/Core и S3, сохраняет `pg_dump -Fc` и offline object volume,
записывает SHA-256 и ID образов, затем поднимает сервисы даже при ошибке копирования.
Каталог копии должен быть новым; других авторов БД/S3 в этот момент быть не должно.

Restore проверяет hashes и версии образов, допускает только новый проект
`asmblyr-restore-NAME` без существующих volumes. Он выполняет `pg_restore`,
восстанавливает object volume и запускает миграции. Используйте отдельный UI port.
После восстановления проверьте вход, число записей, доступ и содержимое файлов.
Env и signing keys сохраняются отдельно от копии БД/объектов.

Для внешних PostgreSQL/S3 оператор организует согласованную копию при остановленных
авторах и восстановление в новые ресурсы. Скрипты локального compose не копируют
внешние облачные bucket и не создают инфраструктуру. Копии содержат пользовательские
данные и credential hashes: храните их приватно и шифруйте средствами backup-системы.

## Восстановить администратора

После сборки Core оператор с доступом к БД может выполнить:

```sh
node scripts/operations/admin-recover.mjs admin@example.test /private/new-credential.json
```

`DATABASE_URL` передаётся через окружение процесса. Команда создаёт приватный файл
с новым случайным паролем, не печатает его и отказывается заменить существующий
файл. Предыдущие способы входа, сессии и OAuth consents отзываются.
Обычных пользователей восстанавливает superuser через ссылку в админке.

## Ключи OAuth

Ключи создаются отдельно от сборки:

```sh
node scripts/operations/create-oauth-keys.mjs .local-data/oauth-keys.json
```

Укажите `OAUTH_ISSUER_URL` и `OAUTH_KEYS_FILE` в окружении Core. Путь к ключам
должен быть доступен из рабочего каталога Core; для локального запуска из
`apps/core` это `../../.local-data/oauth-keys.json`. В контейнере подключайте
приватный файл отдельно и указывайте его путь внутри контейнера. Команда
отказывается заменить существующий файл; не пересоздавайте ключи при обновлении.

## Диагностика

Опциональный [Sentry и локальные p95/p99](../features/monitoring.md) подключаются
в системных настройках. Мониторинг сам по себе не создаёт правила алертов,
retention или dashboards в вашем Sentry: их настраивает оператор.

Воспроизводимый замер API на синтетической схеме запускается только явно.
Из корня репозитория в PowerShell:

```powershell
$env:ASMBLYR_PERFORMANCE_AUDIT = "1"
node scripts/test.mjs core-performance
Remove-Item Env:\ASMBLYR_PERFORMANCE_AUDIT
```

Runner создаёт и удаляет отдельную временную локальную БД. Нужен доступ к локальному
PostgreSQL с правом CREATE DATABASE; удалённая рабочая БД не допускается. Тест
создаёт 40 коллекций/20 000 записей, замеряет список, поиск и глубокую страницу
при 1/8 параллельных запросах, выводит p50/p95/p99, SQL/request и планы поиска.
Это Fastify inject без браузера и внешней сети, для superuser и простой схемы;
он не доказывает производственный SLO или скорость сложных прав/связей.

Для сравнения накладных расходов задайте `ASMBLYR_PERFORMANCE_MONITORING=disabled`
или `enabled`. Enabled использует настоящий Sentry SDK с офлайн-транспортом,
API performance и SQL spans; сеть/доставка в Sentry не измеряются.
`ASMBLYR_PERFORMANCE_SAMPLE_RATE` задаёт долю трассировок от 0 до 1 (по умолчанию 1
в тесте). `ASMBLYR_PERFORMANCE_REPORT` сохраняет JSON в указанный приватный путь.
После проверки удалите тестовые переменные из окружения оболочки.

`/health` проверяет процесс, `/ready` — БД и обязательные миграции.
Логи не должны содержать тела запросов, токены и конфигурационные секреты.
Retentions задаются окружением Core; история бизнес-изменений по умолчанию
не удаляется автоматически. Настройте мониторинг, внешние копии, проверку
восстановления и доставку алертов для своей установки.
