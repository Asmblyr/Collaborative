# Опциональное подключение Yandex Cloud и источники секретов

Дата: 3 октября 2026.

Статус: отложенная идея. Сохранена для будущей работы; внедрение не начато.
Точные интерфейсы, API и модель хранения пока не утверждены.

## Цель

Предусмотреть подключение Yandex Cloud через Workload Identity Federation
для Object Storage и Lockbox. Lockbox должен оставаться опциональным:
Asmblyr можно запускать без Yandex Cloud, сохраняя env и локальные настройки.

## Что есть сейчас

- Core уже поддерживает федеративный обмен OIDC-токена на временный IAM-токен
  для Yandex Object Storage. Конфигурация задаётся через env.
- Федерации сервисных аккаунтов Asmblyr обеспечивают вход внешних сервисов
  в Asmblyr; доступ Core к облаку имеет отдельную конфигурацию.
- Ключ ассистента и SSO client secrets берутся из env. OAuth-ключи читаются
  из серверного файла. Обычные настройки не являются защищённым хранилищем
  секретов; универсального выбора источника и интеграции Lockbox пока нет.

## Предлагаемый вариант на потом

- В настройках добавить облачное подключение Yandex Cloud, которое можно
  выбирать для Object Storage и Lockbox. Права на бакеты и секреты ограничивать
  нужными ресурсами; при необходимости использовать разные сервисные аккаунты.
- Для каждого поддержанного секретного параметра явно выбирать источник:
  переменная окружения, локальное защищённое хранилище или Lockbox.
  Допускать смешанный вариант в одной установке.
- При выборе Lockbox хранить ссылку на secret ID, ключ внутри payload
  и при необходимости version ID. Значение получать только на сервере.
- Секреты, вводимые через настройки для локального хранения, шифровать отдельно
  от обычного JSON настроек. Ключ шифрования не хранить рядом с ciphertext в БД.
- Рассмотреть прямое чтение Lockbox из Core. Альтернатива для deployment:
  External Secrets Operator передаёт значения в Kubernetes Secret и затем env;
  этот способ создаёт дополнительную копию секрета в Kubernetes.

## Условия будущей реализации

- Сохранить существующий env-вариант; не делать облачное подключение обязательным.
- При недоступности выбранного Lockbox сообщать об ошибке зависимой функции,
  не переключаться незаметно на старое значение из env. Получение из Lockbox
  обязательных стартовых секретов, например пароля БД, может блокировать запуск.
- Bootstrap-параметры федерации и источник OIDC-токена должны быть доступны
  до подключения БД. Не создавать цикл «пароль БД ищется в настройках этой БД».
- Определить кеширование, обновление версий и порядок ротации; не читать секрет
  из облака на каждый обычный запрос. Не передавать значения клиенту или в логи.
- Разделить права на использование, изменение привязки и запись секрета.
  Для чтения Lockbox ограничить IAM выбранными секретами; учесть дополнительные
  права при использовании собственного KMS-ключа.
- Перенос существующего значения выполнять отдельно: создать секрет, проверить
  чтение, переключить источник и лишь затем по явному решению удалить оригинал.
  Хеши паролей пользователей и хеши сервисных токенов остаются в БД.
- Lockbox не изолирует доверенные плагины, выполняемые внутри процесса Core;
  границу доступа расширений к секретам определить отдельно.

## С чего начать при возвращении к идее

Уточнить список секретов и желаемый UX, затем согласовать контракт источников,
bootstrap, права и ротацию. После этого выбрать небольшой первый сценарий,
например ключ ассистента из Lockbox при сохранении env-варианта.
