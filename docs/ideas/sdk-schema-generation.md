# SDK с типизированным клиентом и схемой конкретной установки

Дата: 3 октября 2026.

Статус: отложенная идея. Направление сохранено по обсуждению с пользователем;
реализация не начата. Команды, экспорт схемы и fluent API ниже — предложения,
а не возможности текущего SDK. Точные имена и форматы пока не утверждены.

## Цель

Оставить `@asmblyr/sdk` общим HTTP-клиентом, а типизацию пользовательских
и плагинных коллекций получать из конкретной установки Asmblyr. Дать подсказки
коллекций, полей, операторов и результата запроса без специального сборщика
в приложении потребителя.

Системные ресурсы описывает версионируемый контракт Core API и SDK. Версия
админки сама по себе не фиксирует пользовательскую схему: коллекции могут
меняться без обновления Core, UI или SDK. Для них нужен отдельный снимок схемы.

## Что есть сейчас

- SDK — приватный workspace-пакет, ещё не опубликованный в npm. Он принимает
  TypeScript-схему от вызывающего приложения; генерации из сервера и CLI нет.
- Работа с записями идёт через `client.items.list/create/update/...`.
  Фильтры передаются как сериализуемое дерево условий, которое проверяет Core.
- `GET /collections` возвращает метаданные с учётом прав вызывающего пользователя
  или сервиса. Это основа для будущего экспорта, но не готовый контракт генерации.
- В статическом OpenAPI часть операций имеет только `route-only` описание;
  динамические маршруты плагинов не добавляются автоматически. Полной схемы
  коллекций конкретной установки в нём нет.
- OAuth/OIDC для внешних приложений реализован, но токен такого приложения
  не является Core API-токеном. Браузерный вход CLI потребует отдельного
  согласованного доступа к экспорту схемы.

## Предлагаемый пользовательский сценарий

Условные будущие команды:

```sh
npm install @asmblyr/sdk

asm connect --url https://admin.example.com
asm schema pull
```

`connect` связывает локальный проект с установкой и запускает авторизацию.
`schema pull` явно обновляет локальный контракт. Название `clone` оставлено
как первоначальная идея; подключение не копирует данные или саму админку.

CLI можно поставлять как `asm` в пакете SDK либо отдельным пакетом. При выборе
упаковки сохранить небольшой runtime SDK: CLI и генератор не должны попадать
в браузерный bundle. Публикация пакетов и точные команды — отдельная будущая работа.

Предлагаемая последовательность:

1. CLI получает URL установки и определяет адрес Core API и параметры авторизации.
   URL админки и корень API могут отличаться, в том числе из-за BFF `/api`.
2. Открывает браузер для входа и согласия на доступ к схеме. Рассмотреть публичный
   OAuth-клиент с Authorization Code + PKCE и локальным callback; не встраивать
   общий client secret в распространяемый CLI.
3. Получает экспорт доступной схемы без содержимого записей и секретов.
4. Генерирует обычный TypeScript-модуль и сохраняет снимок контракта в проекте.

Для CI и работы без браузера рассмотреть существующий доступ сервисного аккаунта
или другой явно согласованный способ. Токен получать из окружения или хранилища
учётных данных; не включать его в generated-файлы и конфигурацию для Git.

## Типизированный клиент

Пример желаемого API, который пока не реализован:

```ts
import { createClient } from "@asmblyr/sdk";
import { schema } from "./generated/asmblyr";

const client = createClient({
  baseUrl: "https://admin.example.com/api",
  schema,
  accessToken: () => currentAccessToken,
});

const articles = await client.Articles.select((a) => [a.id, a.title])
  .where((a) => a.status.eq("published").and(a.price.gte("1000.00")))
  .orderBy((a) => a.created_at.desc())
  .limit(20)
  .exec();
```

Callbacks выполняются локально над объектами описания полей. Методы строят
существующее дерево фильтра, выбор полей и сортировку; `exec()` отправляет HTTP.
Функции не передаются серверу, исходный код callbacks не разбирается.
Для логики используются `eq/gte/and/or`, а не перехват JavaScript `===`, `>` и `&&`.

Сгенерированный модуль может содержать типы и небольшой runtime-объект с именами
коллекций, полями и связями. Это обычный TypeScript, совместимый со стандартной
сборкой потребителя. Генерация типов не означает runtime-валидацию HTTP-ответов;
её необходимость и стоимость определить отдельно.

`Articles` в примере — стабильный программный alias технического имени `articles`.
Не выводить API-имена из изменяемых отображаемых названий. Определить правила
коллизий, недопустимых идентификаторов и namespace плагинов; сохранить явный
вариант `client.collection("articles")` с подсказками допустимых имён.
Вызов только с generic `collection<"articles">()` не должен быть основным API:
TypeScript стирает аргумент типа, а имя нужно клиенту во время исполнения.

Выбранные поля определяют тип результата, но `where` и `orderBy` продолжают
работать с разрешёнными полями всей коллекции. Учитывать HTTP-envelope ответа,
права и правила добавления первичного ключа; точную форму результата `exec()`
согласовать перед реализацией.

## Что экспортировать и генерировать

- Имена коллекций, режим single/multiple, первичные ключи, обычные поля и связи.
- Отдельные формы Read/Create/Update с учётом прав на каждую операцию.
  Текущие метаданные объединяют видимые для разных операций поля: это объединение
  нельзя выдавать за перечень читаемых полей.
- Типы HTTP-значений, nullable, обязательность при создании, значения по умолчанию
  и доступность записи системных полей. `required` в API и `nullable` в БД различать.
- Большие ID и decimal сохранять согласно реальному строковому HTTP-контракту;
  даты не превращать автоматически в `Date`. Для JSON без вложенной схемы
  не придумывать строгую структуру.
- Подсказки значений состояния и перечислений выводить из подтверждённых
  ограничений. Одни UI choices не гарантируют серверный enum.
- Версию API, версию формата экспорта, хеш или ревизию схемы и версии плагинов,
  влияющих на контракт. Конкретную структуру manifest определить отдельно.

Генерация учитывает права выбранного пользователя или сервиса. Типы отражают
снимок доступного контракта, но не выдают права и не доказывают наличие поля
при другом вызывающем пользователе. Core проверяет актуальные права и значения
на каждом запросе; сохранить существующие ограничения выдачи и записи.

## Плагины и OpenAPI

Коллекции установленного плагина входят в экспорт по тем же правилам, что
и пользовательские, с учётом namespace, версии и доступности. Источник — фактически
установленная схема Core, а не произвольная версия npm-пакета плагина.

Собственные HTTP-методы плагина требуют отдельного описания входа и результата.
Для model handlers рассмотреть уже генерируемые контракты `defineModelContext`;
обычным HTTP-handlers нужен явно поддерживаемый контракт. Схема таблиц сама
по себе не описывает endpoint, а наличие handler не гарантирует JSON-ответ.
Не добавлять параллельную регистрацию actions или вторую реализацию маршрутов.

OpenAPI подходит для HTTP-операций; JSON Schema или отдельный manifest может
описывать коллекции и дополнительную семантику SDK. Выбрать канонический экспорт
и при необходимости формировать OpenAPI из него, не поддерживая расходящиеся
описания вручную. Генератор OpenAPI-типов сам по себе не создаёт fluent API
или runtime-описание полей для него.

## Совместимость и обновления

Снимок схемы и generated-модуль сохранять в Git, чтобы редактор и сборка работали
без постоянного подключения к админке. Обновление SDK не должно незаметно
перетягивать текущую пользовательскую схему.

После изменения коллекций или установки/обновления плагина разработчик явно
выполняет `schema pull` и проверяет diff. Рассмотреть команду `schema check`
для сравнения контракта в CI: удаление или переименование поля, изменение типа,
новое обязательное поле при создании и изменение доступности могут ломать клиента.
Правила совместимости определить отдельно; любое изменение хеша не является
автоматически несовместимым.

Один снимок не фиксирует работающий сервер. Перед deployment проверять его
совместимость с целевой установкой; политика предупреждений или отказа при
несовпадении версий/схемы остаётся отдельным решением.

## С чего начать при возвращении к идее

Сначала согласовать минимальный экспорт коллекций и его доступ. Затем сделать
генерацию типов для существующего `client.items` с сервисным доступом, проверить
правила Read/Create/Update и совместимость. Браузерную авторизацию CLI, fluent API
и типизацию дополнительных методов плагинов развивать следующими отдельными
шагами. Динамический режим SDK без генерации сохранить.
