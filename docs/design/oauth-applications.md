# Asmblyr как провайдер OAuth / OpenID Connect

Статус: реализован первый этап. Вход в сторонние сервисы через аккаунт Asmblyr.
Вход **в** Asmblyr через GitLab остаётся отдельной функцией `AUTH_PROVIDERS`.

## Контракт

- Суперпользователь управляет приложениями на `/oauth-apps`.
- Название, описание, точные redirect URI, включение/отключение и правила допуска пользователей.
- Публичные приложения: `token_endpoint_auth_method=none`.
- Серверные: `client_secret_basic`. Секрет показывается один раз; возможна замена.
- Только Authorization Code с PKCE S256 для обоих типов. Не поддерживаются implicit,
  password grant, динамическая регистрация и client credentials.
- При первом входе пользователь видит приложение, свой аккаунт, получателя и данные
  профиля и явно подтверждает доступ. Согласие сохраняется; отказ возвращает `access_denied`.
- Вход доступен только активным пользователям согласно режиму допуска приложения;
  superuser не обходит ограничения. Отключённое приложение не допускает никого.
- Каждый новый вход проверяет текущую сессию Asmblyr. Старая cookie OIDC не заменяет её.
- Внешние OAuth-токены не дают доступ к Core API, коллекциям или политиками Asmblyr.

## Сохранённое согласие и подключённые приложения

Согласие принадлежит паре пользователь–приложение и содержит audience и одобренные
scopes. Оно сохраняется в PostgreSQL без автоматического срока истечения. Повторный
вход с теми же или меньшими правами автоматически продолжается после проверки
текущей сессии Asmblyr. Срок токенов остаётся 5 минут; срок grants — 10 минут.

Подтверждение появляется снова, если запрошены дополнительные scopes, согласие
отозвано или клиент передал `prompt=consent`. Изменение audience либо добавление
нового redirect URI сбрасывает согласия приложения. Название, описание, смена
секрета и правила допуска сами по себе не отменяют сохранённого согласия.
Актуальная активность аккаунта и допуск приложения проверяются при каждом входе.

На `/settings?tab=applications` пользователь видит только свои подключения:
приложение, разрешения, дату согласия и последний вход. «Последний вход» означает
выдачу authorization code после успешной авторизации у нас, а не подтверждение
создания внутренней сессии сторонним сервисом. GET `/users/me/oauth-apps` возвращает
список; DELETE `/users/me/oauth-apps/:id` отзывает собственное подключение.

Отзыв удаляет согласие и связанные коды, grants и opaque tokens. Другие пользователи
и приложения не затрагиваются. Повторное согласие создаёт новую привязку и не
восстанавливает старые разрешения или токены. Уже выданный JWT может работать
автономно до 5 минут; собственная сессия внешнего приложения может жить дольше.
Завершение внешних сессий (OIDC logout) в этот этап не входит.

Автоматическое продолжение — отдельный POST с `reuse: true`: Core повторно проверяет
сохранённое согласие, аккаунт и interaction cookie. GET и предварительная загрузка
страницы не выдают согласий или токенов. Устаревшая вкладка после отзыва получает
ошибку и предлагает обновить страницу. Блокировки приложения и отдельная привязка
grant к согласию защищают от восстановления отозванного состояния при гонке запросов.

Миграция не переносит исторические события в согласия. После обновления требуется
одно явное подтверждение; прежние краткоживущие grants без привязки не принимаются.
Откат миграции отказывается удалять сохранённые согласия.

## Кто может войти

На вкладке «Доступ» доступны три режима:

- **Все активные пользователи** (`accessMode: "all"`): существующие и будущие
  активные аккаунты Asmblyr. Это значение по умолчанию для новой формы в UI.
- **Выбранные пользователи** (`selected`): только `userIds`. Пустой список
  запрещает вход всем, в том числе суперпользователям.
- **По домену почты** (`domains`): локальная почта входит в `emailDomains` **или**
  пользователь явно выбран в `userIds` («Дополнительно разрешить»).

Проверяется домен после `@`, а не произвольный суффикс. `company.ru` не включает
`othercompany.ru`, `team.company.ru` или `company.ru.evil.com`. Поддомены добавляют
отдельно; маски не поддерживаются. Регистр не учитывается, IDN преобразуются в
ASCII/Punycode; в настройках допустимо начальное `@`. До 100 доменов, хотя бы один
для режима `domains`. Источник — локальная почта аккаунта, не произвольный claim
внешнего провайдера. Это правило допуска, а не проверка владения почтовым адресом:
подтверждение email в Core пока не реализовано, пользователь сам почту профиля не меняет.

Режим `all` не открывает публичную регистрацию и не отменяет подтверждение
передачи профиля. Неактивные аккаунты запрещены во всех режимах, включая исключения.
При сохранении в `all` список выбранных пользователей очищается; вне `domains`
очищается список доменов, чтобы не оставалось скрытых действующих правил.

Миграция сохраняет старым приложениям режим `selected` и их назначения. API без
нового поля `accessMode` также использует `selected` для совместимости. Безопасный
откат возможен только когда все приложения используют `selected` без доменов.

## Профиль

Полей для настройки передачи нет. Стандартные scopes: `openid profile email`.

| Claim     | Источник                                                      |
| --------- | ------------------------------------------------------------- |
| `sub`     | Постоянный UUID пользователя Asmblyr                          |
| `email`   | Локальная почта пользователя                                  |
| `name`    | Имя профиля, если заполнено                                   |
| `picture` | Публичная HTTPS-ссылка на изображение профиля, если заполнена |

Изображение задаётся в настройках профиля. Пароль, `superuser`, политики, внешние
идентичности и токены провайдеров не передаются. `email_verified` не заявляется:
наличие локальной почты не доказывает её подтверждение. В ID/access token также
присутствуют обязательные протокольные поля: issuer, audience, срок действия и т. п.

## Протокол и endpoints

В основе — `oidc-provider` 9.12.2, MIT. Парсинг и проверки OAuth/OIDC принадлежат
библиотеке; Asmblyr реализует приложения, PostgreSQL adapter, доступ и интерфейс.

При issuer `https://admin.example.com/oauth`:

| Endpoint                                  | Назначение                             |
| ----------------------------------------- | -------------------------------------- |
| `/oauth/.well-known/openid-configuration` | Discovery                              |
| `/oauth/auth`                             | Авторизация                            |
| `/oauth/token`                            | Одноразовый обмен кода                 |
| `/oauth/jwks`                             | Публичные RSA-ключи                    |
| `/oauth/me`                               | UserInfo для обычных OIDC access token |
| `/oauth/token/revocation`                 | Отзыв токена через протокол            |

Всегда используйте discovery: клиенту не нужно знать наши пути заранее.
UI проксирует протокол в Core без доступа JS к токенам Asmblyr. Передаются только
cookies провайдера; cookie основной сессии не попадает в протокольные endpoints.
Согласие защищено cookie interaction, авторизацией пользователя и проверкой Origin
на UI. Произвольные forwarded host/proto не меняют issuer. Код живёт 60 секунд,
interaction — 10 минут, токены — 5 минут. Длинные внешние сессии и refresh token
пока не реализованы: клиент начинает новый вход после истечения токена.

## JWT и права внешнего сервиса

Для обычного OIDC audience сервиса оставляют пустым: выдаются подписанный ID token
и opaque access token для UserInfo. Приложению доступны только данные профиля.

Если сервис требует JWT access token, задают audience и допустимые scopes во
вкладке «Интеграция». Выдаётся RS256 JWT с `kid`, точным `aud` и только запрошенными
разрешёнными scopes. Чужой resource/audience и неизвестные scopes отклоняются.
Resource идентифицируется как `urn:asmblyr:application:<client_id>`; клиент с одной
аудиторией может не передавать `resource`. JWT для внешнего ресурса не является
токеном UserInfo. ID token содержит профиль по OIDC scopes.

Список scopes приложения применяется **ко всем допущенным пользователям этого
приложения**. Это не индивидуальная ролевая модель внешнего сервиса. Нельзя
назначать `administrator` широкому списку пользователей ради проверки входа.

Изменение приложения или секрета отзывает его сохранённые коды, grants и opaque
токены. Активность пользователя и актуальные правила допуска проверяются при
согласии, обмене кода и UserInfo, включая изменение локальной почты. Уже выданный
JWT проверяется внешним сервисом автономно и может оставаться действительным
до 5 минут — мгновенный отзыв не обещается.

## Хранение и эксплуатация

- `asmblyr_oauth_apps`: регистрация приложений, `access_mode` и `email_domains`;
  секрет зашифрован AES-256-GCM.
- `asmblyr_oauth_app_users`: назначения пользователей.
- `asmblyr_oauth_state`: зашифрованные данные библиотеки; идентификаторы/коды в ключах
  поиска хешируются. Метаданные для индексов и сроков остаются открытыми.
- `asmblyr_oauth_consents`: долговременные согласия пользователя, audience, scopes,
  время подтверждения и последней авторизации.
- `asmblyr_oauth_grants`: краткоживущие хешированные привязки grants к конкретному
  согласию; очищаются вместе с истёкшим состоянием, не разрастаются как история входов.
- Одноразовое потребление кода атомарно в PostgreSQL, включая параллельные запросы.
- Истёкшее состояние удаляется при старте и каждый час.
- Создание, изменение, замена секрета, выдача/отзыв согласия и успешная авторизация
  (выдача кода) записываются в security events.
- Ключи подписи, шифрования и cookies находятся в отдельном файле вне Git.
- Приложения сохраняются между перезапусками; не используется memory adapter.

Серверный client secret хранится обратимо зашифрованным: библиотеке нужен исходный
секрет для стандартной проверки клиента. Ключ шифрования не хранится в БД.
Файл ключей должен быть доступен только пользователю Core. На Windows настройте
ACL каталога: POSIX `mode` сам по себе не задаёт Windows ACL.

```sh
node scripts/create-oauth-keys.mjs
pnpm db:migrate
```

Core env:

```dotenv
OAUTH_ISSUER_URL=https://admin.example.com/oauth
OAUTH_KEYS_FILE=../../.local-data/oauth-keys.json
```

Не меняйте issuer после подключения клиентов. В production UI и issuer должны
быть на одном origin с HTTPS и доверенным сертификатом. Core размещается за
доверенным прокси; внешний `/oauth/*` направляется в UI. Не логируйте тела token
запросов, Authorization, cookies и OAuth query strings. Добавленная защита
частоты действует на процесс; для нескольких реплик нужны ограничения на ingress.

Скрипт отказывается перезаписывать ключи. Для ротации RSA добавьте новый ключ в
начало JWKS, сохранив старый публичный ключ минимум на время жизни всех токенов.
Ротация ключа шифрования требует перешифрования данных; готовой операции пока нет.
Резервная копия БД без файла ключей не восстанавливает секреты приложений.

## Проверка с LavinMQ

Исследован исходный код **LavinMQ 2.9.3**: management UI использует Authorization
Code + PKCE без client secret. Access token должен быть RS256 JWT. JWKS содержит
`kid`; issuer/audience проверяются. Права берутся из scopes, не из локального
пользователя LavinMQ.

Изолированный пример находится в `infra/oauth-lavinmq`. Порты только loopback:
HTTP issuer на 3000, панель LavinMQ на 15673. AMQP наружу не опубликован. Другой
брокер проекта scrape-stage не изменяется. В демо backend только `oauth`, локальный
пароль guest не даёт обхода SSO.

Регистрация тестового приложения:

- Тип: публичное.
- Callback: `http://localhost:15673/oauth/callback`.
- Audience: `lavinmq`.
- Scopes: `lavinmq.tag:monitoring`, `lavinmq.read:%2F/*`.
- Пользователи: только явно выбранные для проверки.

Это мониторинг и чтение в `/`, без `write`, `configure` и `administrator`.

Локальное демо использует `OAUTH_ISSUER_URL=http://localhost:3000/oauth`.
Браузер обращается прямо к UI на хосте; LavinMQ обращается к тому же адресу
через nginx на loopback внутри общей сети контейнеров. Порт 3000 контейнера
наружу не публикуется. Сертификаты и изменение доверия Windows не нужны.
HTTP допускается Core только для loopback; для production по-прежнему нужен HTTPS.
При смене issuer ранее выданные токены внешних приложений потребуют нового входа.

### Запуск примера и проверки

```sh
node scripts/setup-oauth-lavinmq.mjs
# В apps/core/.env: OAUTH_ISSUER_URL=http://localhost:3000/oauth, затем перезапустить Core
# Создать приложение в UI и указать его Client ID в .local-data/oauth-lavinmq/lavinmq.ini
docker compose -f infra/oauth-lavinmq/compose.yaml up -d
node scripts/test.mjs core-oauth
node scripts/test.mjs core-lavinmq
```

В текущем локальном окружении сначала войдите в админку на `http://localhost:3000`,
затем откройте LavinMQ на `http://localhost:15673` и нажмите «Sign in with SSO».
Существующий callback входящего GitLab SSO остаётся на 3000.

`core-lavinmq` использует одноразовую тестовую БД, временный Core на 3002 и
внутренний HTTP listener 3002. Временно меняет только конфигурацию изолированного
демо-брокера, затем восстанавливает её. Не запускайте эту проверку одновременно
с ручным входом в демо. Рабочая БД и другие брокеры не изменяются.

Проверено 2026-10-02: настоящий LavinMQ 2.9.3 выполнил обмен Code+PKCE, проверил
RS256 через локальный HTTP, вернул тестовую личность через `/api/whoami` и разрешил `/api/overview`.
Запрос `/api/users` был запрещён. Дополнительно пройден браузерный вход на личном
аккаунте: LavinMQ → экран согласия Asmblyr → Overview LavinMQ с текущим пользователем.
Приложение «LavinMQ» сохранено в локальной админке; client ID записан в локальную
конфигурацию брокера. Доступ назначен одному выбранному пользователю.

Дополнительная проверка 2026-10-02: первый вход сохраняет согласие; повторный вход
в том же браузере проходит автоматически; отзыв из профиля возвращает экран
подтверждения. Подключение после проверки восстановлено. 17 тестов Core OAuth и
53 теста UI пройдены, проверки TypeScript и ESLint — без ошибок. Автоматические
тесты используют одноразовую БД и дополнительно проверяют перезапуск, расширение
scopes, смену аккаунта, изоляцию отзыва и запоздавшее сохранение отозванного grant.
