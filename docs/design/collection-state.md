# Системное состояние записи

## Контракт

Опциональное системное поле `status` добавляется рядом с `created_at` и
`updated_at` при создании коллекции. Для существующей коллекции оно включается
в «Настройки коллекции → Состояние».

Начальные состояния:

| Код в API   | Название     | В обычном списке |
| ----------- | ------------ | ---------------- |
| `published` | Опубликовано | Да               |
| `draft`     | Черновик     | Нет              |
| `archived`  | Архивировано | Нет              |

Новые записи получают `published`. У коллекции можно изменить значение по
умолчанию, названия, цвета и видимость состояний; добавить или удалить варианты.
Разрешено 1–20 уникальных кодов. Используемый код удалить или заменить нельзя:
сначала записи необходимо перевести в другое состояние. Переименование подписи
не меняет код или данные. Состояние по умолчанию должно оставаться в списке.

## Хранение и API

`asmblyr_collections.state` — JSONB-конфигурация вида:

```json
{
  "field": "status",
  "defaultValue": "published",
  "statuses": [
    { "value": "published", "label": "Опубликовано", "color": "green", "hidden": false },
    { "value": "draft", "label": "Черновик", "color": "gray", "hidden": true },
    { "value": "archived", "label": "Архивировано", "color": "amber", "hidden": true }
  ]
}
```

Конфигурация передаётся в `POST /collections` или в
`PATCH /collections/:name/settings` как свойство `state`. Отсутствие настройки
означает, что системное состояние выключено. После включения удалить системное
поле или отключить его через API нельзя. Удаление самой пользовательской
коллекции работает по общим правилам.

Физическое поле — `text NOT NULL DEFAULT 'published'` для новой колонки.
Значения проверяются общим валидатором выбора при записи через API; нативный enum
PostgreSQL не используется. Прямые записи в БД не проходят API-валидацию.
Метаданные select и цветного отображения формируются из `state` атомарно вместе
с SQL default. Обычные маршруты изменения структуры и presentation защищены.

При подключении существующего текстового `status` проверяются все непустые
значения. Неизвестные коды необходимо добавить в конфигурацию. Значения, даты и
существующие NULL не перезаписываются, nullability сохраняется; дальнейшая
запись NULL через API запрещена. Обновление других полей записи с историческим
NULL разрешено. Если колонки ещё нет, существующие строки получают default.

Операция блокирует таблицу на время проверки значений и изменения настроек.
Запросы изменения полей проверяют защиту после получения блокировки, поэтому
параллельное подключение состояния не позволяет обойти защиту структуры.

## Список и права

Скрытие реализовано начальным **редактируемым фильтром таблицы**. Он виден над
списком и исключает варианты с `hidden: true`; старые NULL остаются видимыми.
Сброс фильтра показывает все записи. Явный `filter=` в URL сохраняет этот выбор
при обновлении, поиске и пагинации. Явный фильтр ссылки или сохранённый вид имеют
приоритет над начальным фильтром. Для коллекции «один объект» начальный фильтр
не применяется.

Это настройка представления. Обычный API без фильтра, связи и прямые ссылки
сохраняют доступ к записям по текущим правам. Если поле состояния недоступно для
чтения, UI не строит по нему фильтр. Изменять значение могут только пользователи
с правом записи в это поле; default применяется и при отсутствии этого права,
аналогично default других полей. Метаданные состояния скрываются от пользователя,
у которого нет доступа к полю.

Внутренний MCP возвращает конфигурацию состояния и варианты select только для
читаемых полей. Ассистент получает фактический фильтр страницы. Он может учитывать
состояния в существующих `search_items` и `count_items`; скрытие не предоставляет
новых прав и не означает универсальную бизнес-семантику слова «активный».

## Локальное подключение перенесённых данных

2026-10-01 подключены `shops` и `shop_categories` с исходными тремя состояниями.
Проверены контрольные суммы всех строк до и после: 274 магазина и 11 743 категории
сохранены без изменения данных. В начальном списке — 126 магазинов и 3 200 категорий.
Статусы `clients` описывают отдельный бизнес-процесс и автоматически не преобразованы.
