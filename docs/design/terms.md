# Справочник терминов

Администратор объясняет понятия предметной области в общем справочнике, а затем
задаёт точные условия для каждой коллекции. Например, «Активные» в категориях —
`status = published`, а в клиентах может означать `status = active`.

## Интерфейс

- **Настройки системы → Термины** (`/system-settings/terms`): название,
  синонимы, общее определение, включение/выключение. Создание и редактирование —
  в общем нативном боковом диалоге с защитой несохранённых изменений.
- **Настройки коллекции → MCP → Термины этой коллекции**: выбор термина и
  обычный конструктор условий, включая И/ИЛИ и связи на один уровень.
  Условия сохраняются отдельной кнопкой. Все привязки коллекции сохраняются
  атомарно; невалидное условие отменяет всё сохранение.
- Базовые термины: «Активные», «Опубликованные», «Черновики», «Архивные».
  Их можно редактировать и выключать. Новые термины добавляет администратор.
  Миграция создаёт начальные определения один раз и не перезаписывает правки.
- Общее определение само по себе не включает фильтрацию. До настройки
  условия в конкретной коллекции термин для неё не исполняется.
- Изменение названия/синонимов/описания не изменяет точные условия. Отключение
  термина сохраняет его привязки, но прекращает их использование в MCP.

## Хранение и API

`public.asmblyr_terms` хранит определения: UUID, имя, описание, JSONB-синонимы,
`enabled`, отметку базового термина, даты создания и изменения.

`public.asmblyr_collection_terms` связывает UUID коллекции и UUID термина с
JSONB-фильтром. Составной первичный ключ запрещает два значения одного термина
в одной коллекции. Коллекция может иметь до 20 терминов. Удаление коллекции
удаляет её привязки; новая коллекция с тем же именем их не наследует.

Все административные маршруты доступны только человеку-суперпользователю:

| Метод       | Адрес                          | Назначение                           |
| ----------- | ------------------------------ | ------------------------------------ |
| GET, POST   | `/settings/terms`              | Список и создание определений        |
| PUT         | `/settings/terms/:id`          | Изменение определения или выключение |
| GET         | `/collections/:name/terms`     | Справочник и настроенные условия     |
| PUT         | `/collections/:name/terms`     | Атомарная замена всех привязок       |
| PUT, DELETE | `/collections/:name/terms/:id` | Настройка или снятие одной привязки  |

До 100 определений, 12 синонимов на термин. Имя — до 80 символов, определение —
до 1000. Совпадающие без учёта регистра названия/синонимы включённых терминов
отклоняются. На этом этапе термины выключаются, физического удаления через API нет.

Миграция добавляет только служебные таблицы. Автоматический rollback запрещён,
чтобы не уничтожить определения администратора. Структура защищена общим
правилом зарезервированного префикса `asmblyr_`.

## Исполнение через MCP

1. `describe_collection` возвращает применимые `terms`: ID, название, синонимы,
   описание и точный фильтр. Возвращаются только включённые привязки с
   доступными пользователю полями и MCP-коллекциями связей.
   Размер блока ограничен 12 000 символами; `termsPartial` сообщает о неполной
   выдаче, без обрезки отдельных определений или фильтров.
2. `search_items` и `count_items` принимают `terms: [uuid]` или `null`.
   До пяти терминов за вызов. Старые внутренние вызовы без `terms` совместимы.
3. Core загружает актуальные определения и условия. Условия терминов
   объединяются через И с явным/унаследованным фильтром. Группы ИЛИ сохраняют
   смысл. Поиск `q` также остаётся в силе.
4. Вся итоговая выборка проверяется обычным валидатором фильтров: ограничения
   размера, глубины и количества условий действуют на объединённый фильтр.
   SQL выполняется существующим слоем items в read-only транзакции.
5. `conditions.appliedTerms` возвращает фактически использованные определения
   и условия для пояснения ответа. Модель не конструирует их вместо Core.

Отзыв доступа, выключенный MCP, неизвестный/отключённый термин, удалённое поле
или отсутствующая привязка приводят к отказу. Условие никогда не исчезает
молча из запроса. Термины не предоставляют прав и не меняют фильтр таблицы.
Содержимое определений считается данными, а не инструкциями модели.

## Локальное подключение и проверка

Для `shop_categories` настроено «Активные» → `status = published` через UI.
Клиентские записи и состояния при этом не изменяются. У других коллекций
условия автоматически не назначаются.

Проверены административные права, редактирование/отключение, применение через
настоящий внутренний MCP, подсчёт и поиск, комбинации со связями/ИЛИ, отзыв
доступа и атомарный отказ невалидного сохранения. Интеграционные тесты
выполняются через `scripts/test.mjs` в отдельной временной БД.

Справочник закрывает определение бизнес-терминов. На следующем этапе убраны
фиксированные ограничения числа обращений к модели и инструментам: фактические
показатели записываются в телеметрию и выводятся под ответом. Таймаут и ограничения
объёма остаются; подробнее — [телеметрия ассистента](assistant-telemetry.md).
