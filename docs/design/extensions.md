# Расширения: первые соглашения

Дата исследования: 02.10.2026.

Статус: первые соглашения и предложения для обсуждения. Есть kit для серверных
HTTP endpoints, отдельный HTTP SDK и загрузка явно включённых пакетов.
Реализованы декларации коллекций, namespace, реестр владельцев, установка и
добавочные миграции таблиц. Comments включает API и вкладку редактора записи.
Этот документ не заменяет согласование архитектуры с владельцем продукта.

## Что уже есть и согласовано

- Расширение оформляется обычным npm-пакетом.
- Установка опубликованного пакета выполняется через pnpm.
- Локальные расширения разрабатываются в `plugins/` в корне репозитория.
- Первый каркас: `plugins/comments`, имя пакета `@asmblyr/plugin-comments`.
- Метаданные формата: `asmblyr.manifest.version: 1` в `package.json`.
  JSON Schema отложена до расширения манифеста.
- Обязательный `plugin.ts` в корне пакета пока экспортирует `definePlugin({})`
  по умолчанию. Первая возможность — маршруты по файлам `server/api`, без ручного
  списка endpoints. Обработчик экспортируется через `defineHandler()` по умолчанию.
- Публичный API для авторов плагинов находится в `@asmblyr/kit` (`packages/kit`).
  Сейчас это приватный workspace-пакет со сборкой JavaScript и деклараций типов.
- HTTP-клиент находится в `@asmblyr/sdk` (`packages/sdk`): `items.list`, `items.get`,
  `items.create`, `items.update`, `items.delete`, `items.commit`, `users.me`.
  Работает в браузере и Node, обращается к существующему HTTP API.
  Общие контракты записей, фильтров, профиля и ошибок находятся в `@asmblyr/contracts`.
  Админка использует SDK для профиля, чтения, сохранения черновика записи со связями,
  удаления выбранных записей и подписей связей.
- `plugins/*` включён в workspace; comments зависит от локального kit.
  Пакеты устанавливаются в зависимости корневого проекта и явно включаются через
  `asmblyr.plugins` в его `package.json`.
- Core проверяет метаданные до импорта, регистрирует endpoints и обеспечивает
  аутентификацию. HTTP-контракт обработчиков — H3 v2 (закреплена 2.0.1-rc.32).
  `useAsmblyr(event)` даёт actor, requestId, логгер и `items`; стандартные функции H3
  работают с параметрами, телом и ответом. Fastify остаётся сервером Core.
- Пример адреса на UI — `/api/comments/articles/1`, путь в Core — `/comments/articles/1`.
  `/plugins` в адресе нет. Первый сегмент закрепляется за владельцем; конфликты
  с Core и другими плагинами останавливают запуск.
- UI имеет общий проход для endpoints плагинов; он не открывает дополнительные
  маршруты Core. `ui/index.ts` и `@asmblyr/kit/ui` описывают вкладки сохранённой записи.
  Comments добавляет «Обсуждение», проверяет чтение целевой записи и разрешает
  менять/удалять свой текст. Автор берётся из сессии; UI использует общие компоненты Kit.
- Для собственных коллекций есть серверный `storage`: ограниченный namespace
  capability доверенного пакета, без SQL и смены автора. Он не использует grants
  пользователя на внутренние таблицы; плагин проверяет предметные условия
  через обычный `items`. Прямые grants `/items/plugin_…` остаются отдельным путём.
- Kit предоставляет `items.list()` и `items.get()` с правами пользователя или
  сервисного аккаунта текущего запроса. Используется общий с `/items` сервис
  чтения: выбор полей, страницы, сортировка, поиск, фильтры и подписи записей.
  Kit не принимает actor, superuser или разрешённые поля в качестве прав доступа;
  `fields` только сужает проекцию. Фоновое выполнение и Knex не предоставляются.
  Права фиксируются на время запроса. Условия доступа к строкам пока не реализованы
  в общей модели. Полный контракт и ограничения — в `packages/kit/README.md`.
- Kit предоставляет `items.create/update/delete/commit` через общую с HTTP API
  логику записи. Применяются права на действия и поля, проверки связей и история
  с реальным автором. Ответ create/update без права чтения содержит `data: null`.
  Каждая операция атомарна; для нескольких связанных изменений используется
  единый commit. Контракты результата и черновика находятся в contracts.
- Локальный dev-режим сканирует исходники включённых пакетов и перезапускает Core
  при изменении, добавлении и удалении файлов. Сборка формирует `dist/routes.json`;
  production читает этот список и загружает собранный JavaScript.
- Адаптер использует H3Event/toResponse без второго сервера и маршрутизатора.
  Тело ограничено 1 МиБ и буферизуется до обработки; бинарные и потоковые ответы
  проходят через UI. Права, namespace, обработка ошибок и сессии принадлежат Core.
  WebSocket, Nitro lifecycle и потоковая загрузка больших файлов пока не включены.

## Что полезно перенять у Directus

Изучены официальная документация и исходники Directus, ссылки приведены ниже.

| Механизм Directus                                | Что он даёт                                           | Предложение для Asmblyr                                                            |
| ------------------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Метаданные `directus:extension` в `package.json` | Тип, пути сборки и исходников, совместимость с host   | Небольшой манифест в `package.json`, проверяемый до загрузки кода                  |
| Разделение App / API и hybrid extensions         | Раздельные среды исполнения                           | Общее описание в `plugin.ts` и отдельные результаты сборки для Core и UI           |
| Bundle с несколькими entries                     | Один устанавливаемый пакет для связанного функционала | Несколько компонентов внутри обычного плагина, без отдельного типа bundle          |
| SDK, composables и общие UI-компоненты           | Переиспользование возможностей продукта               | Документированный kit и доступные через него компоненты интерфейса                 |
| Filter / action hooks                            | Изменение операции и реакция на событие               | Явно определить транзакцию, порядок, права и ошибки каждого обработчика            |
| Sandbox с requested scopes                       | Изоляция API-кода с ограниченными возможностями       | Отдельно проектировать изоляцию, если появится потребность в недоверенных плагинах |

У Directus уже есть SDK, типизированные определения расширений, проверка манифеста,
сборка, наблюдение за изменениями и очистка зарегистрированных обработчиков.
Это действующие механизмы, а не отсутствующие у него возможности.

Обычные API-расширения Directus получают внутренние services, Knex, env и emitter.
В документации Services явно указано, что отсутствие `accountability` или `null`
использует административные права. В исследованном `ItemsService` контекст
нормализуется в `null`, а часть проверок payload выполняется при его наличии.
Это сильный внутренний интерфейс, требующий аккуратности от автора расширения.

## Предлагаемые правила

### 1. Одинаковый пакет для локальной разработки и установки

- Имя и версия определяются стандартными полями npm.
- Источник пакета не меняет его контракт: локальный workspace, npm и приватный
  реестр используют один формат.
- Установка делает пакет доступным. Подключение задаётся явным списком
  `asmblyr.plugins` в корневом `package.json`.
- Пакеты разрешаются относительно корня проекта. Это учитывает строгую структуру
  зависимостей pnpm и даёт Core и UI один список подключений.
- Подключение проверяет дубли имён, наличие сборки и совместимость до исполнения
  кода. Одинаковое имя из двух источников не должно приводить к случайному выбору.

### 2. Пакет может расширять Core, UI или оба сразу

- `plugin.ts` сохранён как точка описания; его дальнейшую роль определим отдельно.
  Обработчики Core размещаются в `server/api`, UI entry — в `ui/index.ts`.
- Плагин может добавлять несколько обработчиков и компонентов. Новый вид
  компонента не требует нового устанавливаемого пакета.
- Сейчас TypeScript компилирует серверное описание в JavaScript. Пакет экспортирует
  собранный `plugin.ts` через основной `exports`, предоставляет `./package.json`
  и сгенерированный список маршрутов через `./routes`.
  `./ui` экспортирует отдельный браузерный entry; Next генерирует статические
  импорты включённых пакетов, не импортируя их серверные entry points.
- Серверные зависимости и секреты не входят в клиентскую сборку.
- Первое подключение UI происходит во время сборки Next.js. Добавление или
  удаление плагина в production требует новой сборки UI и перезапуска Core.
- Для связанного функционала предлагаем включение целого плагина. В Directus
  bundle допускает отключение отдельных entries через `partial`; нам такую
  возможность следует вводить после определения зависимостей компонентов.

### 3. Kit для расширений, SDK для HTTP-клиентов, contracts для общих типов

- Расширения используют документированные экспорты kit. Импорты из
  `apps/core/src`, `apps/ui/src` и внутреннего состояния страниц не поддерживаются.
- Пакет `@asmblyr/kit` экспортирует `definePlugin`, H3 `defineHandler`,
  `useAsmblyr`, типы плагина, endpoint и чтения данных, а также `EndpointError`. Отдельные server и ui entrypoints рассмотрим при
  реализации первых возможностей, если потребуются разные зависимости.
- `@asmblyr/sdk` оборачивает HTTP API: URL, query, токен или cookies, ошибки и отмену.
  Он не импортирует внутренние сервисы Core, Knex или PostgreSQL. Пользовательские
  коллекции типизируются через generic-схему клиента; публичные системные типы
  переиспользуются из `@asmblyr/contracts`.
- Core использует contracts и собственные сервисы. Внутри Core не нужен HTTP-запрос
  к самому себе; kit использует те же проверки прав и чтение, что HTTP-маршруты.
- В дальнейшем kit должен предоставить операции с данными, регистрацию обработчиков, ошибки,
  логирование и согласованные точки расширения интерфейса.
- Требуемая версия API расширений указывается отдельно от версии самого плагина.
  Несовместимый явно подключённый плагин выдаёт понятную ошибку запуска или сборки.
- Официальные плагины используют тот же публичный контракт, что сторонние.
- Документация каждого API включает типы, пример, ошибки, правила авторизации
  и транзакционное поведение. Одних TypeScript-типов недостаточно.

### 4. Контекст выполнения обязателен

- Для пользовательского запроса Core связывает контекст kit с авторизованным пользователем.
- Плагин не передаёт список разрешённых полей и произвольный actor в каждую операцию.
  Общие сервисы Core выполняют проверки прав, связей, валидацию и проекцию ответа.
- Отсутствующий контекст приводит к ошибке. Перехода к superuser по умолчанию нет.
- Для будущих фоновых операций предлагается явно назначенный сервисный аккаунт
  с политиками. Режим выполнения нужно будет описать вместе с первой такой задачей.
- Собственные маршруты плагина требуют аутентификации по умолчанию. Публичный
  маршрут, если он потребуется, объявляется отдельно и проходит отдельную проверку.
- История сохраняет инициатора изменения и происхождение операции от плагина.
  Конкретную модель хранения происхождения согласуем перед изменением схемы.
- Это контракт kit. Код доверенного Node.js-плагина в процессе Core технически
  может обращаться к ресурсам процесса; такой режим не является песочницей.

### 5. Интерфейс расширяется в определённых местах

- Первой точкой для comments предлагается обсуждение существующей записи:
  контекст коллекции и записи, текущий пользователь, доступные действия.
- Конкретное место выбираем при проектировании comments: карточка записи или
  существующая плавающая панель. Наличие двух отдельных обсуждений не предполагается.
- Доступ к данным выполняется через API. Скрытие кнопки не заменяет проверку Core.
- UI получает явный контракт контекста и callbacks. Поиск DOM-элементов страницы,
  изменение глобального store и подмена внутренних компонентов не являются API.
- Компоненты и токены оформления доступны через публичные экспорты. Основа UI
  остаётся shadcn; React и библиотека UI подключаются как совместимые peer dependencies.
- Для редакторов полей сначала расширяется ввод существующего типа хранения.
  Собственный SQL-тип потребует отдельного контракта схемы, валидации и миграций.
- Локальная граница ошибок может показывать сбой UI-компонента. Она не обеспечивает
  изоляцию произвольного кода плагина.

### 6. У данных плагина есть владелец и жизненный цикл

- Первый образец формата: `plugins/comments/server/collections/entries.ts` с
  `defineCollection()` из kit. Локальное имя, первичный ключ, системные даты,
  типизированные поля и настройки отображения находятся в одном описании.
  `required` и `nullable` задаются независимо. Общие типы полей, ключей и дат
  вынесены в contracts и используются Core и kit.
- Описания обнаруживаются Core; при первом запуске создаются таблицы и метаданные.
  Обновление поддерживает `defineMigration` с `addField` и `addIndex`.
  Связи и разрушительные изменения декларациями пока не поддержаны.
- У comments namespace `comments` в `asmblyr.manifest.namespace`. Коллекция `entries`
  устанавливается как `public.plugin_comments_entries`. Core резервирует `plugin_`,
  проверяет длину имён, конфликты и владельцев. Реестры `asmblyr_plugins` и
  `asmblyr_plugin_collections` создаются обычной миграцией Core.
- Первоначальная установка всех включённых коллекций атомарна, с общей блокировкой.
  Хранится нормализованное описание; повторный запуск сохраняет данные. Изменение
  или удаление установленного описания, смена namespace/владельца и конфликт с
  чужой таблицей останавливают запуск. Обновление существующего описания требует
  отдельной миграции. `server/migrations` выполняются по порядку в той же транзакции;
  журнал `asmblyr_plugin_migrations` обнаруживает удалённые/изменённые планы.
- Операции с пользовательскими коллекциями проходят через контекст kit и сервисы Core.
  Хранилище самого плагина не даёт доступ к чужим записям.
- Миграции выполняются отдельным управляемым этапом, с учётом текущей версии
  и блокировкой параллельного запуска. Они не запускаются из обработчика запроса.
- Отключение, удаление пакета и уничтожение его данных являются разными действиями.
  Отключение и удаление пакета сохраняют данные.
- Структура и настройки коллекций с `plugin_` защищены в API и редакторе, в том
  числе для superuser и при отключённом пакете. Строки обслуживаются общими items
  с обычными правами. Скрытие из навигации не является ограничением доступа.
  Пользовательские связи с этими коллекциями пока также запрещены.
- Настройки делятся на серверные и разрешённые для UI. Плагин получает только свои
  настройки, а не весь объект окружения Core.

### 7. События имеют описанную семантику

Каталог событий сейчас не создаём. Следующие требования применим при первом
реальном обработчике:

- До записи: обработчик может отклонить операцию или вернуть изменённые значения.
  Перед сохранением Core проверяет итоговые данные и разрешения заново.
- Несколько обработчиков исполняются в определённом порядке. Операции используют
  общий контекст пользователя; недоступные поля не выдаются обработчику автоматически.
- Транзакционные изменения, история и связанные данные завершаются вместе.
  Ошибка обработчика до завершения транзакции отменяет операцию.
- Событие после сохранения означает завершение внешней транзакции целиком,
  включая массовые и вложенные операции. При rollback такое событие не публикуется.
- Ошибка внешней реакции после commit не должна выдавать сохранённую запись за
  несохранённую. Для гарантированной доставки понадобятся outbox, повторы и
  идемпотентные обработчики; обычная подписка в памяти этого не гарантирует.
- Циклические вызовы требуют явного учёта цепочки. Полное отключение проверок
  или всех событий не должно становиться стандартным способом остановить рекурсию.
- Подписки и ресурсы имеют процедуру освобождения. Горячее отключение серверного
  кода и выполнение непроверенного кода пока не входят в первый этап.

## Ближайшее решение

Чтение и запись данных с контекстом пользователя и проверкой разрешений реализованы,
а HTTP SDK выделен в отдельный пакет с общими контрактами.
Коллекция comments устанавливается при первом запуске, namespace и владелец
фиксируются в реестре. Выполнен полный путь: добавочная миграция, API комментариев,
UI-вкладка с общими shadcn controls и защитой неотправленного текста.
Демонстрационный `/comments/status` перенесён в тестовый стенд Core. Рабочий пакет
содержит только API обсуждения. `useStorage(context, declaration)` выводит типы
из декларации; UI импортирует shadcn-компоненты из `@asmblyr/kit/ui/<component>`.
Админка использует те же реализации; передача компонентов через provider удалена.
Следующие возможные шаги: связь жизненного цикла записи с обсуждениями, модерация,
события и уведомления. Редакторы текстовых полей теперь подключаются через
`defineUiPlugin({ fieldInterfaces })`; пример `plugins/color` содержит ввод,
отображение и настройки палитры для каждого поля. Полный контракт —
[Kit / Редакторы полей](../../packages/kit/FIELDS.md). При отключении пакета
сохраняются значения и метаданные; UI использует стандартное поле.

Второй пример — `plugins/overview`: отдельная UI-страница и собственный endpoint
чтения контекста пользователя. `defineUiPlugin({ pages: [...] })` регистрирует
маршруты `/extensions/<namespace>/<id>` и пункты группы «Приложения».
Меню, страницы и вкладки используют общий список активных пакетов и границу
ошибок отрисовки. Изменения админки для регистрации следующих страниц не нужны.
Отдельные права на страницы и вложенные маршруты пока не реализованы.
Третий пример — `plugins/calculator`: общий контракт действия, HTTP/MCP,
подготовленный результат и форма с dirty/busy. Защищены переходы ассистента и
замена формы новым результатом; общая защита всех переходов страниц ещё впереди.
Действие — обычный h3-обработчик в `server/api/*.post.ts`, обёрнутый
`defineModelContext<Input>` с `defineModelAnnotation`. Сборщик выводит runtime
схемы из TypeScript. HTTP-маршрут обнаруживается по файлу; обёртка явно публикует
тот же обработчик для ассистента. В `plugin.ts` регистрация не дублируется.
Подробности — `docs/design/plugin-actions.md` и `packages/kit/LIFECYCLE.md`.

Манифест описывает формат пакета, `plugin.ts` — его возможности. Настройки
конкретной установки и секреты в эти описания не входят. Кроме явно перечисленного
в разделе «Что уже есть и согласовано», правила выше остаются предложениями.

## Реализовано: возможности, hooks, настройки

Пакет декларирует возможности в manifest; проект явно разрешает их по имени пакета.
Kit проверяет их вместе с правами пользователя. Файлы `server/hooks/*.ts` используют
`defineHook`, а `server/settings.ts` — `defineSettings`; `plugin.ts` остаётся пустым.
В админке доступна страница **Система → Плагины**. Comments использует настройки
и транзакционную очистку. Актуальные правила, примеры и границы —
[capabilities](../../packages/kit/CAPABILITIES.md) и [hooks/settings](../../packages/kit/HOOKS.md).
